# Deliverable 21 — Getting the iOS Collector through a Developer account

What stands between the code in `ios/` and a build on a device, in TestFlight, or on the App Store.

The list is split by who can do each item. Everything in §1 is mechanical and already done.
Everything in §2 requires a Mac and cannot be verified from this repository's CI, which is Linux.
Everything in §3 requires an Apple Developer account and a human in a web form.

**The honest summary: the project is configured, and it has never been compiled.** No `xcodebuild`
exists in this environment, so the app target has never been type-checked. The Swift package's
tests pass, but they pass on Linux, where every `#if canImport(CoreBluetooth)`,
`canImport(CoreLocation)`, `canImport(NetworkExtension)`, `canImport(UIKit)` and
`canImport(SQLite3)` branch evaluates false and compiles to nothing. That is most of the code that
touches a radio. Budget for a first build that does not succeed.

## 1. Already configured

| Item | State |
|---|---|
| Bundle identifier, team, signing style | `ios/Config/Signing.xcconfig`, overridable per developer — see §3.1 |
| `Info.plist` | Complete: purpose strings, orientations, launch screen, file sharing, version from `MARKETING_VERSION` |
| Export compliance | `ITSAppUsesNonExemptEncryption=false`. SHA-256 over a package is a digest, and nothing here encrypts |
| Privacy manifest | `PrivacyInfo.xcprivacy`, verified present in the target's Copy Bundle Resources phase |
| App icon | Single 1024×1024, the form Xcode 14+ accepts. Generated by `ios/Tools/make-app-icon.py` |
| Entitlement | `com.apple.developer.networking.wifi-info` declared — but see §3.2, the App ID must match |
| Background mode | `bluetooth-central` only, and it is genuinely used. `location` was removed rather than left declared and unused |
| Deployment target | iOS 16.0, iPhone and iPad |

## 2. Requires a Mac: do these first, in this order

**2.1 Build the Swift package alone.** `cd ios/Packages/RFMapper && swift test`. This already passes
on Linux, so on macOS it additionally type-checks the `canImport` branches that Linux skipped. Any
error here is in the capture layer and is worth fixing before the app target confuses the picture.

**2.2 Build the app for the simulator.** `open ios/RFMapperCollector.xcodeproj`, scheme
`RFMapperCollector`, any iOS 16+ simulator. No signing needed. This is where unbuilt SwiftUI and
wiring errors will appear.

Expect to touch the `#if canImport` providers. They are the least-verified code in the repository:
written against the CoreBluetooth, CoreLocation and NetworkExtension documentation, reviewed, and
never compiled.

**2.3 Do not trust simulator data.** A simulator has no Bluetooth or Wi-Fi radio. The app will run,
the UI will work, and a package exported from it will contain no radio observations. `project.yml`
keeps the simulator as a supported platform because it is what makes the interface iterable, not
because it can collect anything.

**2.4 Run on a device.** Needs §3.1 and §3.2. Then verify, in this order, because each depends on
the previous one:

1. Bluetooth permission prompt appears when you start a session — not at launch. The
   `CBCentralManager` is constructed lazily on purpose.
2. BLE rows accumulate on the Live tab.
3. Location permission prompt appears, and GNSS rows appear at roughly one per 30 s.
4. A `WIFI_ASSOCIATION` row appears with a real BSSID and **a blank RSSI**. Blank is correct — iOS
   does not disclose the associated network's signal strength, and the row carries
   `metadata.permission_degraded` with `WIFI_RSSI_UNAVAILABLE_ON_IOS` saying so. If the BSSID is
   empty or all zeroes, the entitlement or the location permission is missing and the session's
   degradations will say `WIFI_INFO_UNAVAILABLE`.
5. Export a day. Confirm the file appears in the Files app under the app's folder.

**2.5 Validate the exported package against the Master.** This is the check that matters more than
any of the above, because it is the one the whole cross-language contract exists for. Copy the
exported `.zip` off the device and import it:

```bash
# --tests needs the variant task, not the aggregate `test`, which rejects the option
cd android && ./gradlew :data-room:testDebugUnitTest --tests '*IosPackageContractTest*'
```

That test reads the committed fixture. To check *your device's* package instead of the fixture, drop
it into `contract/` and point the test at it, or import it through the Master app. A package a real
iPhone produced should import with no structural issues at all; if it does not, the bug is in the
Swift export path and is worth fixing before any more field work.

## 3. Requires an Apple Developer account

**3.1 Set your team and bundle identifier.** Create `ios/Config/Signing.local.xcconfig` — it is
gitignored:

```
DEVELOPMENT_TEAM = A1B2C3D4E5
PRODUCT_BUNDLE_IDENTIFIER = com.yourcompany.rfmapper
```

The team identifier is the ten-character string under Membership details in the Developer portal.
Do not edit `Signing.xcconfig` itself, and do not put these in `project.yml` — a target setting
overrides its own xcconfig, so that would silently disable the override.

**3.2 Register the App ID with the Wi-Fi entitlement.** This is the one item that will fail in a
confusing way if skipped: the build installs fine in the simulator, then refuses to install on a
device with a provisioning-profile error.

In Certificates, Identifiers & Profiles → Identifiers, create an App ID matching your bundle
identifier and enable **Access WiFi Information**. It is a standard capability on any paid account —
no special request, unlike `NEHotspotHelper`, which is granted only to hotspot-provisioning apps and
which this app deliberately does not use.

With automatic signing, Xcode creates the profile once the App ID exists. If the app builds but
`NEHotspotNetwork.fetchCurrent` returns a network with an empty BSSID, this step is why.

**3.3 Decide whether you need the App Store at all.** Three routes, and the cheapest sufficient one
is usually right:

| Route | Ceiling | Review | Use when |
|---|---|---|---|
| Development signing | 100 registered devices, profile expires yearly | None | Your own survey handsets. Almost certainly this one |
| TestFlight internal | 100 App Store Connect users | None for internal testers | A small team, over-the-air updates |
| TestFlight external / App Store | 10,000 / public | Yes | Only if handing this to people outside your organisation |

This is a private site-survey tool for enrolled hardware, not a consumer app. Development signing
covers it, and it skips §3.4 and §3.5 entirely.

**3.4 If you go to App Store Connect.** Create the app record, then:

- **App Privacy**: answer **Data Not Collected**. This is accurate and worth getting right — the app
  has no network code, no analytics and no third-party SDKs. Observations stay in a local SQLite
  database and leave only as a package the operator exports by hand. The `PrivacyInfo.xcprivacy`
  already declares this, and the questionnaire must agree with it.
- **Export compliance**: `ITSAppUsesNonExemptEncryption=false` is already set, so the questionnaire
  is skipped.
- Privacy policy URL (required even with no data collection), support URL, description, screenshots,
  age rating.

**3.5 If you face App Review.** Two things will draw questions, and both have honest answers:

- *Why Bluetooth?* The app records advertisements and signal strength to map wireless coverage. It
  never connects to a peripheral. The purpose string says exactly this.
- *Why background Bluetooth?* Service-filtered scanning for enrolled tags. Note that the app does
  **not** claim background location; if you later add CLBeacon monitoring you will need to restore
  the `location` background mode, add `NSLocationAlwaysAndWhenInUseUsageDescription`, request Always
  authorization, and justify all of it.

Provide a demo account note explaining there is no account, and a build that works without one. A
reviewer with no enrolled tags and no site model should still see the app run, which it does — the
session screen states what each mode can and cannot see before anything is collected.

## 4. Functional gaps, in the order they are likely to matter

None of these block a signed build. They are what the app does not yet do.

| Gap | Consequence |
|---|---|
| No site-model or device-registry import | The operator types the observer identity, building and zone by hand, and the app cannot stamp `target_device_id`. Attribution happens entirely at the Master, which is correct by policy but means the Collector cannot show *which enrolled device* it just saw |
| No CLBeacon region monitoring | Capability matrix §7 lists it as optional. It is the only route to background zone presence that survives app termination, and the reason background location would be worth re-adding |
| No survey-point capture | The Android Collector can record a fingerprint at a marked point; iOS cannot, so an iOS device cannot contribute to a fingerprint survey. On an association-only site this does not matter at all |
| No in-app import of a derived package | Viewing results is the Master's job. Fine as a division of labour, but it means an iOS-only deployment has no way to see its own output |
| Xcode scheme has no test target | `⌘U` does nothing. Package tests run from the command line or by selecting the package scheme |
| `reconfigure` on the providers is unused | `CollectorModel` tears down and rebuilds providers between sessions instead. Dead code, harmless, untested |

## 5. What is actually verified, so the gap is clear

| Verified on Linux, by test | Not verified anywhere |
|---|---|
| Observation model and its invariants | Every `canImport` branch: BLE, location, association, UIKit, the SQLite store |
| CSV dialect, row checksums, canonical JSON | The app target and all SwiftUI views |
| `Double` formatting matching Java's | Permission prompts and their denied paths |
| SHA-256, and the deterministic zip writer | The `Access WiFi Information` entitlement end to end |
| Export manifest, and its refusal to disagree with its rows | Signing, provisioning, archiving |
| Byte-identity with the committed contract fixture | Whether any of it runs on real hardware |
| `ObservationFactory`'s identity decisions | Battery and thermal behaviour over a long session |

The left column is the file contract, which is the part that would be expensive to get wrong
silently. The right column is everything an hour with an iPhone and a Mac would settle.
